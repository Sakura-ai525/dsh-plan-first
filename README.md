# dsh-plan-first

一个 DeepSeek Harness 插件：**先对齐，后开工**。

装上并打开之后，每个新对话里你提要求，Agent 不会立刻开始干活，而是先做一轮

1. **可行性** —— 能不能做，关键限制和前提是什么；
2. **我的理解** —— 它打算做什么、不做什么，把有歧义的地方点名；
3. **方案** —— 有可行路径就给出，有多条就说明差别；
4. **收益与风险** —— 各自得到什么、可能付出什么代价、回滚难不难；

然后**停下来等你确认**。确认之后才动手。

## 效果对比

之前：

> **你**：帮我把这个项目改成支持多语言
>
> **Agent**：（立刻开始改文件……）

之后：

> **你**：帮我把这个项目改成支持多语言
>
> **Agent**：
> **可行性**：……
> **我的理解**：我打算……，不打算……，其中「X」我不确定，需要你定
> **方案**：A 方案……；B 方案……；我倾向 A，因为……
> **收益与风险**：……；风险是……，回滚成本……
> 等你确认，确认后我再开始改。

## 什么情况下不拦

插件不是「一律先问」。以下情况 Agent 会直接执行，避免把简单事情拖成两轮：

- 纯问答、解释概念、查资料；
- 只读操作：读文件、搜索、查看状态；
- 需求已经具体到没有歧义（做什么、改哪里、怎么改都说清了）；
- 你说「直接做」「别问了」「就按这个来」或给出类似授权。

需要对齐的是这几种：需求有多种解读、要写入/修改/删除文件、要跑有副作用的命令、有多种方案可选、做错代价高且不易回滚。

## 安装

本插件以 GitHub 仓库形式发布。在 Harness 的**插件**页里安装：

```
github:你的用户名/dsh-plan-first
```

装完**完全退出 Harness 再重新打开**（桌面上是右键托盘图标退出，不是只关窗口）。

> 桌面版 profile 由应用独占管理，`dsh plugin --profile desktop add …` 会被拒绝，请走插件页安装。

## 怎么开关

装好之后，**插件**页里这个插件下面就有开关——和其它插件一样，点一下就能开关，不需要额外设置页。

- **打开** → 之后新建的对话一律走「先对齐后开工」；
- **关闭** → 立刻恢复原来的直接执行模式。

### 生效范围

| 情况 | 行为 |
| --- | --- |
| 打开开关后**新建**的对话 | 立即生效 |
| 打开开关时**已经开着**的对话 | 沿用当时已组装的提示词，不受影响 |

这是 DSH 系统提示词的组装方式决定的：每个会话在开始时组装一次自己的提示词。所以「开关」天然等于「对之后的新对话生效」。

## 配置（可选）

如果不想用插件页的开关，也可以在 profile 的 `cordis.patch.yml` 里按 `id: plan-first` 覆盖：

```yaml
- id: plan-first
  config:
    enabled: false        # 关掉，但保留插件
    appendix: '……'        # 追加你自己的补充规则，会接在内置规则后面
```

改了之后需要重启 Harness。

## 设计边界（请先读这条）

**这是提示词层面的软约束，不是运行时拦截。**

它显著提高「先对齐」的概率，但不保证 100%。以下情况 Agent 仍可能判断为「无需对齐」而直接做：

- 你的消息很短、语气很急；
- 客观上只有一种合理做法，它认为不存在需要对齐的分歧；
- 模型本身的判断偏差。

真正的硬拦截需要在工具调用层面动手——那会把「误拦了你本来就想让它做的事」这个风险带进来，并且会明显拖慢正常流程。本插件刻意不做这一层。

如果你想要更硬的约束，可以在 `appendix` 里追加更严格的措辞；如果发现某个场景总是漏拦，直接改 `lib/prompt.js` 里的分类规则更有效。

## 原理

一个 `systemPrompt.section`，`order: 88`，`text` 每次组装提示词时求值。

```js
scope.systemPrompt.section({
  name: 'app:plan-first',
  order: 88,
  text: () => buildInstruction(options)
})
```

- 不注册每步提醒（`systemPrompt.context`），不碰工具调用，不改任何运行时行为 —— 所以它不可能弄坏一个会话；
- 注册挂在插件自己的 fiber 上，插件被禁用/卸载时 section 自动消失，没有需要清理的状态；
- Harness 没有 `systemPrompt` 服务时静默降级，不会导致加载失败；
- 不声明 `Config` schema，因此不受 schemastery 版本差异影响；
- 不声明 `dsh.compatibility` 版本范围，因此不会因为版本区间写错而被 loader 跳过。

`order: 88` 是与现有插件错开的：社区插件 `dsh-thinking-language` 占用 85（它的 section）和 1000（它的每步提醒）。

## 自定义

改 [`lib/prompt.js`](lib/prompt.js) 里的 `INSTRUCTION_LINES` 即可，改完跑：

```bash
node test/smoke.mjs
```

测试会检查文案里关键要素还在不在（可行性 / 方案 / 收益与风险 / 等确认 / 逃生门 / 只读豁免等），以及篇幅有没有膨胀到挤占上下文的程度。

## 开发

无依赖，直接用 Node 跑测试（Node >= 20）：

```bash
node test/smoke.mjs
```

## 兼容性

| 场景 | 行为 |
| --- | --- |
| Harness 没有 `systemPrompt` 服务 | 静默不生效，不报错、不影响加载 |
| 插件页开关关闭 | fiber 销毁，section 从下一次组装中消失 |
| `enabled: false` | 不注册任何东西 |
| 与 `dsh-thinking-language` 共存 | 序号错开，互不覆盖 |
| 与 `dsh-reasoning-only-guard` 共存 | 一个改提示词、一个包流，无交集 |
